7. MEMORY SAFETY
================================================================================
ASan + UBSan clean on treasury_yields, weather_wide, mixed_types, usgs_quakes,
with output byte-identical to the release build.

`leaks` found a real leak in the new decoder path: the three arrays holding
grouped columns' exception data were freed at the fail_ids label and nowhere
else, so every SUCCESSFUL decode of an archive with a 2D group leaked them.
11 leaks / 400 bytes on treasury_yields, 0 on a three-row file -- which is what
identified it as data-dependent and therefore new. Fixed; 0 leaks on compress
and restore for all three datasets since.

Three pre-existing unchecked indices found by reading and fixed: the dictionary
walk (sgroup[], cut[]), the text walk (sgroup[]) and the 2D group loop (cut[])
all indexed by counters driven from the column list without bounds-checking
against the arrays' real lengths. Reachable from a crafted archive.
test_hostile does not catch these -- its mutations damage bytes rather than
build a coherent header that lies about its own shape. That is a fuzzer gap.

10. THE OTHER TWO ALL-OR-NOTHING SCREENS -- both measured, both stay
================================================================================
The numeric gate was all or nothing and one blank cell cost 41% of the yield
curve. Two screens have the same shape. Both measured end to end over 21
tables; neither should change.

A. THE 50% DICTIONARY THRESHOLD
A column is dictionary-encoded only if its distinct count is at most half its
row count. One row over and it falls to text, which gets the least modelling.

  threshold      0.5 (ships)      0.6         0.75        0.9
  total            9,710,712   9,719,505   9,850,119   9,948,278
  vs shipped           0.00%      +0.09%      +1.44%      +2.45%

Raising it loses, and it keeps losing as it rises. This CONFIRMS the earlier
result (4-14% worse) and, more usefully, DISPROVES the hypothesis attached to
it. The theory was that raising the threshold failed only because dictionary
parents were unmeasured, and that fixing that (20dd96e) would unblock it. That
fix has been in for two sessions and the threshold still loses. The
prerequisite theory was wrong; drop it.

Per file it is genuinely mixed at 0.6 -- nyc_311 gains 5.0% (376,335 ->
357,394) and nyc_collisions 0.3%, while chicago_crimes loses 1.4%,
chicago_permits 1.8% and usgs_quakes 1.0%. So the right threshold is
file-dependent, and picking it per file would mean another double encode --
which section 6 has just shown is the most expensive thing in this codec.
Not worth it for +0.09%.

B. THE EXACT-DECIMAL RULE FOR 2D GROUPS
A group requires prev.dec == col.dec EXACTLY, so one column quoted to a
different number of decimals ends the run however similar the quantities are.
Relaxed to "within one decimal place":

  every table that forms a group at all:  +0 bytes. Total 4,492,243 either way.

It changes nothing. On weather_hourly the looser rule forms 2 groups where the
strict rule forms 0 -- and the end-to-end guard then rejects both, so the file
is byte-identical. The strict rule is costing nothing on this data, and the
guard is visibly doing its job on the one case where the rule was the only
thing standing in the way.

CONCLUSION: the all-or-nothing lesson does NOT generalise to these two. It was
specific to the numeric gate, where the discarded column was large, smooth and
the sole gateway to the planar predictor. Worth having asked; worth writing
down that the answer was no.

13. WHY THE TEXT PATH IS NEAR ITS LIMIT -- the finisher shootout
================================================================================
Before hunting for a better text algorithm, measure the ceiling. The real text
blob from six datasets, against every strong finisher on this machine:

  finisher                total      vs xz -9e
  xz -9e (ships)      2,263,479          0.00%
  7z LZMA2 -mx9       2,266,396         +0.13%   (same algorithm)
  brotli -q11 lgwin24 2,371,255         +4.76%
  zstd -22 --long=27  2,460,015         +8.68%
  7z PPMd             2,735,845        +20.87%

NOTHING BEATS xz -9e. PPMd is normally the strongest thing available on
natural-language text and loses by a fifth, because this blob is short
structured strings, not prose.

Consequence: there is no better coder to switch to, and a substitution stage
(FSST, OnPair, BPE) would have to beat xz's own match finder. BtrBlocks
(SIGMOD 2023) measured plain zstd BEATING Dict+FSST on a real string column,
13.6x against 8.0x -- and xz just beat zstd by 8.68% here, so the gap would be
wider. Those codecs trade ratio for RANDOM ACCESS, which the archival path does
not need. Their proper home in this project is the `ondemand` branch.

FSST+ (CWI, 2025) independently confirms the front-coding work: its entire
contribution is common-prefix elimination over lexicographically sorted
dictionary entries, and it reports 2.2-2.8x from that alone.

THE PRINCIPLE THAT FOLLOWS. xz already finds every repeat inside its window;
what it PAYS for is distance, since a match costs bits proportional to
log(distance). So the lever is not "find more repeats", it is "make similar
things closer". Row reordering and front-coding are both instances of it, and
they are the only two text ideas that have ever worked here.

Tested and rejected the same day: reordering the string groups inside the blob
so similar columns sit together. -0.29% overall, wins on 5 of 16, best case
chicago_crimes -2.7%. Not worth a format change; that lever is exhausted.

The one remaining lead with evidence is semantic, not compressive: in the
numeric-extraction data, usgs_quakes.time has 16,190 distinct values and a
skeleton with ONE, and splitting wins 9.8% on that column. A real timestamp
parser -- not generic digit splitting, which loses on seattle_fire911.datetime
and nyc_311.created_date -- is the only text idea left with data behind it.

14. ORGANISING PARTLY-REPETITIVE TEXT -- four designs, measured
================================================================================
The question was organisational, not which compressor to use: how should a
column that is partly repetitive be ARRANGED? A column is either dict
(alphabet + ids that collapse into runs under a parent) or text (raw strings).
The 50% threshold is a cliff -- a 60%-distinct column gets nothing from the 40%
of rows that do repeat.

Four organisations, per text column, against what ships:

  A HYBRID   repeated values -> alphabet + ids, singletons -> raw text
             (removes the cliff without paying for singletons in the alphabet)
                                                              +1.10%
  B SORTED   singletons sorted and front-coded plus an explicit
             permutation to undo it (what SortComp does)      +9.48%
  C FRONT    front-code the text column as stored              +5.56%
  D BOTH     hybrid with its singleton run front-coded         +4.88%

All four lose on average. But the average hides the result, and the individual
rows are where it is:

  weather_hourly.time     9,438 ->    434    21.7x
  weather_wide.time       2,660 ->    325     8.2x
  treasury_yields.Date    5,757 ->  4,637   -19.5%
  chicago_crimes.date    13,304 -> 21,517   MUCH WORSE

>>> THE DISCRIMINATOR IS MONOTONICITY, NOT TEXT-NESS <<<
Consecutive timestamps share ~14 of 16 characters. Timestamps in arbitrary row
order share none. chicago_crimes is not in date order; weather_hourly is.

WHY EVERY CHEAP NOMINATOR FAILED, measured end to end:
  cheap per-group probe (lzma preset 1, group alone)          +2.50%
  prefix ratio >= 0.3 / 0.5 / 0.7                +3.29% / +2.45% / +0.57%

The reason is the useful part. A long shared prefix IS a long LZ77 match, and
xz already codes it cheaply. Front-coding REMOVES the anchor xz was matching
on. It only pays where the strings are short enough that xz's per-match
overhead dominates the bytes saved. High prefix sharing is necessary and
nowhere near sufficient.

THE DESIGN THAT WORKS: nominate by prefix ratio, DECIDE on the whole blob, cap
at the top 3 candidates so the cost stays bounded.

  dataset            text pile      after      gain
  weather_hourly         9,438        434    -9,004   (-95.4%)
  weather_wide           2,660        325    -2,335   (-87.8%)
  treasury_yields        5,757      4,637    -1,120   (-19.5%)
  seattle_fire911      258,888    258,323      -565
  14 others                              exactly +0
  TOTAL              3,366,752  3,353,728   -13,024   (-0.39%)

NEVER WORSE on any dataset. Archive level: treasury_yields -3.2%,
weather_hourly -1.8%, weather_wide -0.6%. Cost: at most 3 extra text-pile
compressions, which is far cheaper than the second full encode the exceptions
guard needs.

NOT BUILT -- it is a format change (per-group front-coding flags in smeta
rather than one archive-level flag) and was left for a decision.

column is MONOTONIC in stored order: consecutive timestamps share ~14 of 16
characters, so weather_hourly's time column goes 9,438 bytes to 434. No corpus
dataset is time-ordered -- chicago_crimes' date column is in arbitrary row order
and front-coding it is 62% WORSE -- so the guard declines on all 13 and those
archives come out byte-identical.
