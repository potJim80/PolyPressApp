How PolyPress works

PolyPress compresses data tables (CSV, TSV, JSON, Parquet) without losing a single character. It doesn't compress the table as one block of text. It works out what each column is, rearranges the data so the patterns line up, and only then hands it to xz. This page follows one small table through every step, as the code stands on 2 October 2026.

Read→ Derived columns→ Kinds→ Numbers→ Reorder→ Pack→ xz→ Check

The example: six crime reports, cut down from the Chicago crimes table PolyPress is tested on. Real tables have thousands to millions of rows; the steps are the same.

1Read the table

The reader takes CSV, TSV, other delimited text, JSON and JSON Lines directly; Parquet goes through a small Python helper first. Every cell is kept as the exact bytes it was written with, so 011 stays 011 and 41.88119 doesn't become 41.881190.

  • Text must be valid UTF-8 (or the encoding you name with --encoding). A bad byte is refused, never guessed at.
  • A row wider than the header is refused unless the extra cells are empty.
  • Excel, Stata, SPSS, SQLite and already-compressed files are recognised at the door and refused with a plain message.

Why so strict: a check that runs after the damage can't see the damage. An early version read every file leniently, turned bad bytes into "?" before the table existed, and then "verified" the corrupted table against itself.

2Derived columns

Some columns repeat numbers that another column already holds. location above is just longitude and latitude pasted into a template. PolyPress finds numbers like these and swaps each one for a short reference to the column it came from:

POINT (-87.627811 41.881203)   →   POINT (⟨source 1⟩ ⟨source 0⟩)
POINT (-87.627902 41.88119)    →   POINT (⟨source 1⟩ ⟨source 0, rounded to 5 places⟩)

Now every cell in the column looks the same, and a column that repeats one value is almost free to store.

  • The search runs on a sample of 500 rows. A column becomes a source if it explains a number in at least half the sampled rows, with up to 4 sources per column.
  • A reference is either an exact copy or a rounding (half to even) to fewer decimals. Numbers longer than 64 characters are never referenced.
  • Sources are never derived themselves, so restoring always expands from finished values.

Measured: chicago_crimes −19%, nyc_collisions −16%, nyc_311 and seattle_fire911 −12% each, and 5.1% across the 39 test tables. Tables with nothing to derive come out byte-for-byte as before. It also makes compression slightly faster, because there's less text left to handle.

3Sort the columns by kind

Every column becomes one of three kinds:

kindrulein the example
numericevery cell is a plain number that prints back exactlyid, latitude, longitude
dictionaryfew distinct values: at most half the rows, and at most 65,536district, primary_type, arrest, location
texteverything else(none here)

Numbers are stored as whole numbers scaled by their decimals. 41.881203 with 6 decimals becomes 41881203. The column must print back to its exact original text, or it isn't numeric.

Nearly-numeric columns. latitude has a blank cell, so strictly it isn't numeric. In a real table that's one blank among thousands of rows. If at most 5% of cells are odd (blanks, -0.0, a stray extra decimal), the odd cells are stored separately by position and as text. Their slots are filled with the neighbouring value, so the column keeps its full length. A quick trial compression decides this for each column, once every dictionary column is known: stay numeric only if that could beat the dictionary or text form. The numeric side counts the option of being sorted by a parent (step 5).

Dictionaries. For each column, the distinct values are found with a hash table, sorted, and each cell is replaced by its position in that sorted list. primary_type becomes BATTERY=0, NARCOTICS=1, THEFT=2 and the column becomes 2 0 2 2 1 0.

Measured: four blank cells in 72,048 once cost 41% on the Treasury yield curve, because one bad cell turned a whole column into text. That's why nearly-numeric columns exist. The per-column decision is from today. It used to be one decision for the whole table, and on a CDC vaccination table that made the archive 3.77 MB instead of 2.73 MB.

4Predict the numbers

Numbers compress best when the stored value is small. PolyPress stores what's left after a prediction, not the number itself.

Down a column: differences. id is 1001 1002 1003 1004 1006 1007. Its differences are 1001, 1 1 1 2 1: one starting value, then tiny numbers. PolyPress tries differences of order 0 to 4 (differences of differences) and keeps the order whose packed size is smallest.

Across columns: 2D groups. Three or more neighbouring numeric columns with the same decimals and sizes within 8× of each other form a group, like a grid of sensor readings or interest rates. Each cell is predicted from the cell above, the cell to its left, and the one diagonally between. Only the double difference is stored.

Measured: 2D groups give 1.66× to 2.14× on yield curves and sensor grids, the shape this step was built for. Survey data has codes, not quantities, so this step correctly stays out of the way there.

5Reorder by a parent

Nothing extra is stored for the new order. The parent is restored first, so the restorer can redo the same sort and put every row back. The sort is stable: ties keep their original order.

  • Choosing parents. On a sample of up to 40,000 rows, PolyPress measures how much each column tells you about each other column (conditional entropy). It builds a tree: the most predictable column is the root, and each other column hangs under the parent that helps it most.
  • Then it checks. A quick trial compression of the column in its new order against its original order. If reordering doesn't actually make it smaller, the parent is dropped. The score only nominates; the trial decides.
  • Text columns can have a parent too. Up to 5 candidates are nominated, each one is tried, and the smallest result wins.
  • Numeric columns can have a parent too. This is new on 2 October, and it's for tables where many places are each measured over time: sorted by county, a county's daily counts sit next to each other and their differences shrink. The candidate is picked by counting the bits its differences would need in each order (no compression involved), then confirmed with a quick trial. Numeric parents are chosen before the 2D groups form, because a group keeps file order.
  • The sorts are counting sorts on the dictionary positions: one pass over the rows, no comparisons.

Measured: numeric parents took a CDC vaccination table (3,300 counties × dates) from 2.73 MB to 1.69 MB, 25% under plain xz, and the 100 open-data tables down 5.3% overall. Trusting the score without the check once made a real table 66% larger. Adding the check took 19.7% off the CDC disease-surveillance table, the one PolyPress was already best at. The same idea was published by AT&T in 2012 (US 8,312,026, now expired); PolyPress arrived at it independently.

6Pack into bytes

Everything goes into two byte streams: one for numbers and one for text.

Numbers stream

  • Dictionary positions at a fixed width: 1 byte when there are up to 256 values, 2 bytes up to 65,536.
  • Other numbers in "zigzag" form, so −1, 1, −2 become 1, 2, 3. Each number takes 1 byte; anything 255 or larger gets a marker byte plus 4 or 8 bytes at the end.
  • The positions of the odd cells from step 3, stored as gaps.

Text stream

  • The dictionary values, sorted, so neighbours share their start. Each one is stored as "how many characters match the previous value" plus the rest (front-coding): BATTERY stays whole, and BATTERY_X after it is just 7 + _X.
  • Text columns, one cell per line, in their parent order.
  • The odd cells from nearly-numeric columns.

A small description, the metadata, records each column's kind, decimals, parent, and how many bytes belong to which column. It's written as JSON.

7Three xz streams

The metadata, the numbers and the text are each compressed once with xz at its strongest setting (-9e). xz has layout settings, and each stream gets its own:

streamsettingswhyeffect
numberslc0 lp2 pb2fixed-width values: position predicts better than the previous byte−2.2%
textlc4 pb1more weight on the previous character−0.1%
metadatadefaultsmall

The numbers and text are compressed at the same time on two threads. The archive is: PPZ2, then the three compressed lengths, then the three streams.

Measured, and rejected: a separate xz stream per column was worse (+0.85% numbers, +1.5% text). Patterns shared between columns are worth more than keeping them apart. Choosing settings per table would add 0.6% but needs a trial compression every time. xz's "extreme" mode stays: turning it off saves 13% of the time but makes files 0.13% bigger.

8Check, then write

Before anything is written, the archive is decoded again and every cell is compared with the original. The file is written under a temporary name and renamed into place only if the check passes. If you stop it halfway, nothing is left behind.

Every choice above is made once, in a single pass. There are no "try three ways and keep the smallest" steps; the only trials are the quick, cheap ones inside steps 3 and 5. You chose that on 29 September: 2.3× faster for files about 2.5% bigger, and today's improvements have since won that size back.

Determinism: the same table always gives the same bytes, on any Mac and with any number of threads. Scores are rounded to a fixed grid before they're compared, and ties go to the leftmost column. The tests check that one thread and four threads write identical files.

9Big files

A file too big to hold in memory is cut into blocks of rows, and each block is compressed exactly as above. With the default 1 GB limit, NEMSIS (53 million rows) became 1,475 blocks of 36,065 rows each.

  • Compress while reading: one thread reads the next block while four workers compress, and the blocks are written in order. Nothing waits for a round to finish.
  • An index at the end of the file lists every block's size and the column names.
  • Progress is reported as it goes, which is what the app's progress bar shows.

Measured on NEMSIS (6.8 GB of CSV): 19.5 minutes → 2 minutes 3 seconds this week, with the archive unchanged byte for byte. The gain came from code, not more memory or cores: a bug fix (blocks were running one at a time), compressing while reading, and half the sorting work removed.

10Restoring

Restoring runs everything backwards:

  • Unpack the three streams.
  • Rebuild each parent before its children, and redo each parent's sort to put the rows back.
  • Add the differences back up.
  • Put the odd cells back.
  • Expand the derived references.

The output can be any format: CSV, TSV, JSON, JSON Lines or Parquet.

The restorer assumes the archive might be damaged or made by someone else. Every count, size and position in it is checked against the bytes actually present before it's used. The tests feed it hundreds of truncated, bit-flipped and deliberately lying archives; each one must be refused or decode cleanly, never crash.

Speed: all 100 benchmark tables restore in about 5 seconds. Restoring needs no trial compressions and no choices.
